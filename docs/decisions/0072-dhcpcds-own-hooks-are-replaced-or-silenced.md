# 0072: dhcpcd's own hooks are replaced or silenced, never left alone

Status: accepted
Date: 2026-08-03
Milestone: the open question [0071](0071-a-client-with-no-socket-is-stopped-by-the-pid-it-wrote.md) closed with

## Context

[0066](0066-a-lease-reports-its-nameservers.md) found netcfgd and dhcpcd both
writing `/etc/resolv.conf` and whichever ran last winning, and ended it by passing
`-c`, which replaces dhcpcd's whole hook directory. That was the `DHCPv4` client.
**The `DHCPv6` client got nothing**, and 0071 wrote it down as the next thing to
answer. It is not a hypothetical -- measured against a real dnsmasq and a real
dhcpcd 10.1.0 over a veth pair:

```
# dhcpcd -6 -b cli
# cat /etc/resolv.conf
# Generated by dhcpcd from cli.dhcp6, cli.ra
search v6.example
nameserver 2001:db8:44::53
```

On any machine where netcfgd's DNS mode owns that file and the document says
`config = "dhcp6"`, dhcpcd was writing it behind netcfgd's back. The same
contention 0066 closed, on the family nobody had run.

## Decision

**What netcfgd does about dhcpcd's own hooks is a type with two arms, and no third
one meaning "nothing".**

```rust
enum DhcpcdHooks<'a> {
	Replace(&'a str),   // -c <script>: the DHCPv4 client, which also reports
	Silence,            // -C resolv.conf -C hostname: the DHCPv6 client
}
```

`Silence` rather than `Replace` for `DHCPv6`, and the reason is the report contract
rather than dhcpcd:

**The interface report is one file per interface.** `/run/netcfgd/reported/<iface>`
is written whole by whoever writes it, and the generated hook rewrites it on every
lease event. An interface with both `dhcp` and `dhcp6` would have two clients
holding the same file, each rewriting it with its own family's `dns=` lines and each
clobbering the other on every renewal -- resolvers that flap with the renewal timers
of two independent leases. So the `DHCPv6` client is not given a script that reports;
it is stopped from writing the files netcfgd owns, which is the whole of the defect.

`-C <name>` matches `<name>`, `NN-<name>` or `NN-<name>.sh`, read out of
`dhcpcd-run-hooks` itself rather than taken from the manual page -- so `resolv.conf`
silences `20-resolv.conf` and `hostname` silences `30-hostname`.

**On the hostname half, which is not measured and says so.** `30-hostname` reads
`$new_dhcp6_fqdn` for a `DHCPv6` lease -- it is in the hook, line 151 -- so the path
exists. Nothing here could make it fire: option 39 is not in Debian's default request
list, and a server sending one unasked did not produce it either. It is silenced
anyway, because the *other* client's `-c` already silences the same hook and two
families behaving differently about the machine's identity is worse than one flag
whose effect could not be shown. That is stated here rather than left to be
discovered.

## What the test is worth

`tests/live/dhcpcd.sh` grows a `DHCPv6` half with dnsmasq as the server -- one
package, real stateful DHCPv6, and the router advertisement whose M flag is what
makes a client ask at all. The counter-proof runs first, exactly as the `DHCPv4` half
does:

```
ok   a DHCPv6 lease's own hooks rewrite the resolver file too
ok   netcfgd starts a DHCPv6 client
ok   and a DHCPv6 lease reaches the interface
ok   and dhcpcd left the resolver file alone this time
ok   and the hostname with it
ok   and dropping dhcp6 stops the client, which named its own pid file
```

**A negative check with no event of its own needs a bound somebody measured.**
dhcpcd installs the address and calls its hooks afterwards, so "the file was not
written" is satisfied by "not written *yet*" -- 0070's race in its other form. There
is no positive signal to wait for here, because the whole assertion is that nothing
happens. So the check waits twice as long as the counter-proof needed for the entire
exchange *in the same run on the same machine*, which is a bound that scales with a
loaded machine rather than a sleep somebody guessed. Removing the `-C` flags fails
that check on every run.

The last line is 0071's dhcpcd arm getting its first live exercise: `delegation.sh`
covers stopping an odhcp6c, and nothing had stopped a `dhcpcd -6`.

## Consequences

- `config = "dhcp6"` on a machine with dhcpcd no longer rewrites `/etc/resolv.conf`.
- A `DHCPv6` lease's nameservers still reach nothing, and that is now a deliberate
  gap rather than an accident: the report cannot carry two clients, and making it
  able to is a change to a contract other people write to
  ([docs/interface-report.md](../interface-report.md)).
- `+0 KB`: two flags and an enum.

## What is still open

**A DHCPv6 lease's nameservers.** The shape that would work is a fragment directory
-- `reported/<iface>.d/<writer>`, merged by netcfgd -- which is an additive change to
the report contract and wants its own decision, including what a merge means when two
writers disagree and what happens to a fragment whose writer died. Worth doing when
something needs it; today `dhcp6` on a WAN takes its resolvers from the document or
from the `DHCPv4` lease beside it.

**Nothing silences a client netcfgd did not start.** All of this is about processes
netcfgd runs. A dhcpcd started by the distribution's own unit, on an interface
netcfgd manages, is a different question and the answer is not a flag.
