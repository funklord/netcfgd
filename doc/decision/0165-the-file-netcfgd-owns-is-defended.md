# 0165: the file netcfgd owns is defended

Status: accepted
Date: 2026-09-06
Milestone: M8; the second half of the resolv.conf report that
[0164](0164-the-grant-has-to-be-the-directory.md) opened

## The report

"You need to overwrite resolv.conf no matter what, if another process tries to
stop you kill it."

0164 had just made the write *possible* under the systemd sandbox. This is
about it *staying* written.

## What was measured

A running daemon with `on_drift = "reconcile"` and
`dns_mode = "write_resolv_conf"`, and a shell standing in for another resolver:

```text
after netcfgd applied:   nameserver 192.0.2.53
another daemon writes:   nameserver 203.0.113.99
after 12s of the loop:   nameserver 203.0.113.99
```

Unchanged, under a file whose first line reads *"# Generated by netcfgd. Edits
will be overwritten."*

## Two filters, either of which alone was enough to lose it

**The observation asked netcfgd's record, not the file.** `build` fills
`observed.dns` from `prior.dns` -- what netcfgd wrote down as having
delivered -- so a foreign overwrite was invisible by construction. The planner
compared desired against a record that still said "delivered", found no
difference, and emitted nothing. That is `evidence.md`'s *ask the object you
mean, not something correlated with it*: the record is a fact about what
netcfgd did, and the question is what the file says now.

**The drift loop drops anything that is not an interface's.**
`reconcile_drift` restricts a plan to the interfaces that opted into
reconciling, and `Op::DnsApply` answers `None` to `interface()` -- correctly,
because a host's resolver is not an interface's property. So `restrict` could
only ever drop it, whatever any policy said. A second gate sat above it:
`reconcile_drift` returns early when no interface is reconciling, and a machine
whose only reconcilable state is `global { dns { .. } }` has none.

Each was proven load-bearing by reverting it alone and watching
`tests/live/resolv_owned.sh` lose the file both times.

## Decision

**The observation reads the file back, and the drift loop may act on the
host.**

`read_resolv_currency` re-renders what netcfgd would write from the scopes it
recorded delivering, compares it with the file, and clears `observed.dns` when
they differ -- so the planner sees nothing delivered and re-applies. It is the
fourth currency check of this shape, after an access point's passphrase (0052),
a tunnel's configuration (0053) and a `WireGuard` key (0135), and it lives
beside them in `host::augment` for the reason they do: `build` stays a pure
function of a netlink snapshot.

Only for `write_resolv_conf`. Every other mode hands the file to a resolver
that owns it, and comparing bytes netcfgd does not write would report drift for
another daemon doing its job.

`Op::is_host_wide_config` names the ops that configure the host rather than an
interface -- `dns.apply` and `hostname.set` -- and `restrict` keeps them when
the *global* drift policy says reconcile. **An allow-list, not
`interface().is_none()`**: `commit.arm`, `commit.confirm` and `commit.revert`
answer `None` too, and sweeping a confirm window into a drift pass would apply
something nobody asked for. A test asserts that, and fails when the rule is
written the tempting way.

**A rewrite loop would be worse than the fault**, since a false difference
would rewrite `resolv.conf` for ever. Measured over a two-scope configuration,
which is where a re-render could disagree with what was written: zero rewrites
in 25 seconds with nothing touching the file, and the live test pins it.

## The killing, and why the mechanism is `Conflicts=`

The instruction was to kill whatever interferes. For the daemon that actually
interferes here, a kill does not hold: `systemd-resolved.service` carries
`Restart=`, so a signal gets it restarted seconds later and netcfgd would be
fighting a supervisor rather than a program.

**`netcfgd-exclusive.conf` gains `Conflicts=systemd-resolved.service`**, with
the `After=` that 0145 records as necessary -- `Conflicts=` alone orders
nothing. That is how systemd is told to stand a daemon down and keep it down,
and it is the same mechanism already used for NetworkManager, systemd-networkd,
connman, wpa_supplicant and ModemManager. resolved's absence from that list was
the fifth omission of exactly that kind, and it is the one that owns this file.

It stays in the **opt-in** drop-in rather than the packaged unit, because a
machine using `dns_mode = "resolved"` wants resolved running and netcfgd
handing scopes to it -- the arrangement 0007 recommends. Conflicting with it by
default would break that configuration for everyone to fix this one.

## Consequences

- `tests/live/resolv_owned.sh` drives a running daemon: netcfgd writes the
  file, a foreign write lands, netcfgd puts its own back, the foreign server is
  gone, and nothing is rewritten while nothing changes. It also reads the
  drop-in for the half no machine here can drive, since there is no
  systemd-resolved on them.
- `netcfgd-observe` gains a dependency on `netcfgd-dns`, which depends only on
  the model, so no cycle. `resolv_conf_path` became public in `netcfgd-apply`
  rather than being copied, since a second copy is a second thing to be wrong.
- **What is still not done is killing an unsupervised writer.** With the above,
  netcfgd wins every round within a loop tick, so a competing writer produces a
  visible flap rather than a lost file. Killing one is an optimisation on that
  and is not in this record.
