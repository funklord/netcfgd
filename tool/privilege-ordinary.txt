# Config keys reviewed and found ordinary -- safe for a client that is not
# root to send, under decision 0127.
#
# This file is an acknowledgement, not a permission list. Nothing reads it at
# run time; `c/src/daemon/privilege.c` decides what is privileged and
# everything else is ordinary by construction. What this exists for is the
# gap that leaves: a key added to the compiler later would be ordinary
# because nobody looked at it. `tool/privilege_gate.py` refuses a key that is
# in neither this file nor `privileged[]`, so adding one costs somebody a
# decision.
#
# Review it as a list of things a desktop user may set on this machine's
# network. The question for each is not "is this sensitive" but "does this
# grant more than configuring the network" -- a wifi passphrase is sensitive
# and ordinary; `tun { owner }` is neither sensitive nor ordinary, because it
# hands a device to somebody.
#
# Keys that are privileged in ANY block are absent here and live in
# `privileged[]` instead, even where the same word is ordinary elsewhere:
# `config` is an addressing list in an interface and an .ovpn path in an
# openvpn block, and the gate matches on the name. `privilege.c` keeps the
# block-sensitive answer; this file keeps the coverage. That is also the
# gate's blind spot, and it hid `block_list { file }` behind `openvpn { file }`
# until 10.761 -- a new key whose NAME is already privileged somewhere is not
# asked about here, so ask about it when adding it.
#
# Reread for the C on 2026-11-09 (0317): the Rust's reader also took value
# words from its match arms (`auto`, `peap`, `wpa3`), which the C's does not,
# so those are gone; the keys below the blank line are the ones the C
# accepts and nobody had classified, and `remote { agent }` among them was
# privileged and went to the table instead (10.760).
